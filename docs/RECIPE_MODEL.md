# Модель рецепта — Phase 04

`src/features/recipes/model/` — самостоятельный модуль данных. Он не зависит от React, CSS, хранения файлов, печатного макета и экспорта. Публичные функции и типы доступны через `index.ts`.

## Структура

`Recipe` содержит UUID `id`, `schemaVersion: 1`, даты `createdAt` и `updatedAt` в ISO 8601 UTC, название, описание, категорию, теги, сведения о приготовлении, группы ингредиентов, шаги, метаданные изображений, заметки, советы и необязательную пищевую ценность. Пустые строки и массивы допустимы в черновике. Порядок групп, ингредиентов внутри группы и шагов задаётся положением в массивах; отдельный индекс не хранится. ID остаются у сущностей при перестановке.

`Ingredient` содержит ID, название, необязательное конечное неотрицательное числовое `amount`, единицу и необязательную заметку. Стандартные единицы: `g`, `kg`, `ml`, `l`, `pcs`, `tsp`, `tbsp`, `pinch`, `to_taste`. Пользовательская единица задаётся `{ kind: 'custom', label: '...' }`; стандартная — `{ kind: 'standard', code: 'g' }`. Для «по вкусу» количество можно опустить. Дробные значения, например `0.5` и `2.25`, сохраняются без вычислений или округления. `IngredientGroup` содержит ID, необязательный заголовок и массив ингредиентов.

`CookingStep` содержит ID, обычный многострочный текст `instruction`, необязательные заголовок, длительность, температуру, заметку и массив `assetIds`. HTML-подобные теги в инструкции отклоняются. `MediaAsset` хранит только ID, имя файла, MIME-тип изображения, положительные целые ширину и высоту, альтернативный текст и роль `cover | step | gallery`. Ссылки шага проверяются по существующим ID изображений. Бинарные данные и base64 не входят в JSON рецепта.

`Nutrition` необязательна, но при её наличии обязателен `basis`: `per_serving`, `per_100g` или `per_recipe`. Калории, белки, жиры и углеводы необязательны и должны быть конечными неотрицательными числами. Модель не рассчитывает их автоматически.

## Проверка и версии

`validateDraftRecipe(value)` проверяет техническую корректность данных и разрешает пустой рецепт. `validateCompleteRecipe(value)` дополнительно требует непустое название, хотя бы один ингредиент с названием и содержательный шаг. Обе функции возвращают `{ success: true, data }` либо `{ success: false, issues }`; каждый issue содержит `path`, `code` и читаемое `message`. Валидация не исправляет входные данные и не мутирует их.

Zod-схемы отклоняют неизвестные поля, неверные типы, повторяющиеся ID, несуществующие медиа-ссылки, некорректные UTC-даты и `updatedAt` раньше `createdAt`. Явное `undefined` в необязательных полях отклоняется: такие поля следует опускать, чтобы JSON не терял данные.

Текущая версия схемы — 1. `deserializeRecipe` проверяет версию до разбора по схеме и выдаёт `RecipeModelError` с кодом `unsupported_version` для других числовых версий. Это точка для будущих миграций; миграций из несуществующих версий сейчас нет. Невалидный JSON даёт `invalid_json`, несоответствие текущей схеме — `invalid_recipe` с массивом issues.

## Использование

```ts
import {
  createEmptyRecipe,
  createIngredient,
  createIngredientGroup,
  createCookingStep,
  validateCompleteRecipe,
  serializeRecipe,
  deserializeRecipe,
} from '@/features/recipes/model'

const recipe = createEmptyRecipe()
recipe.title = 'Омлет'
recipe.ingredientGroups = [
  createIngredientGroup({
    ingredients: [createIngredient({ name: 'Яйца', amount: 2 })],
  }),
]
recipe.steps = [createCookingStep({ instruction: 'Взбейте яйца и обжарьте.' })]

const complete = validateCompleteRecipe(recipe)
if (complete.success) {
  const restored = deserializeRecipe(serializeRecipe(complete.data))
  // restored сохраняет значения, ID и порядок элементов.
}
```

Фабрики принимают необязательные `id` / `createId`, а `createEmptyRecipe` — `now`, чтобы тестировать ID и время без глобальных подмен. Три реалистичных набора данных находятся в `__fixtures__/` и используются только тестами.
